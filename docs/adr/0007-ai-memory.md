# ADR 0007：AI 记忆

- 状态：已接受（2026-10-25），第一、二、三期已实施
- 涉及：`ik-ai`（`memory.rs`、`memory_jobs.rs`、`memory_admin.rs`、私信准备与定稿、工具箱）、`ik-messaging`
  （跨会话取最近消息、翻聊天记录）、管理后台（「AI 记忆」页）、主站（对话里的「记住了」提示）
- 业务规则：`docs/business-rules/ai-assistant.md` 第 13 节（MEM-001～100）、WF-011

## 背景

迁移后 AI 只有**短期记忆**：私信每次带当前代际最近 40 条消息（LLM-001），评论按（帖、评论者、AI）带之前的问答（CTX-003）。
用户能感觉到的问题有两个：

1. **聊久了会断片**：超过 40 条以后更早的内容直接丢掉。
2. **换个会话就失忆**：AI 会话每次新建（CONV-012），新会话里 AI 对这个人一无所知。旧系统 AstrBot 有
   `recall_long_term_memory` 一类长期记忆，迁移时没有迁过来（ADR 0004 待决问题 2）。

目标按用户体验定：像一个认识你的朋友——不断片、换会话也认识你、会关心你说过的事、记得准、说得自然、
你能看到它记了什么并且能改、私信里的事不会出现在公开场合、不变慢。

## 决策

### 总体：四层记忆，全部在 PostgreSQL 里，分三期

| 层 | 内容 | 期 |
|---|---|---|
| 工作记忆 | 当前会话最近的原文 + 窗口外的滚动摘要 | 1 |
| 近期衔接 | 48 小时内同一角色其他会话的最后几轮 | 1 |
| 长期记忆 | 用户档案（所有角色共享）、关系记忆（每个角色单独） | 1 |
| | 事件记忆（带时间，按相关度检索）、待跟进事项（到期主动问起） | 2 |
| 原文档案 | 聊天原文 + `recall_history` 工具翻旧账（按关键词与日期） | 3 |

档案与关系记忆每类最多 40 条，全部带上比检索更准，也没有检索延迟。事件记忆按话题检索（见下）。

### 第一期的设计要点

1. **写入在回复链路之外**。摘要在准备阶段发现窗口快满时入队；长期记忆在回复定稿时入队，用同一个任务键把执行时间
   往后推（默认 180 秒），对话停下来之后才提炼一次。首帧延迟、总预算、降级链都不变。
2. **用户说「记住」时当场生效**。私信里提供 `remember` / `forget` 两个进程内工具，时间线发 `memory.saved` /
   `memory.forgotten`，主站可以显示「💭 记住了：…」。日常信息靠后台提炼，不靠模型主动调用（减少误记和延迟）。
3. **提炼用「增删改」而不是只追加**（借鉴 mem0）：模型拿到已有记忆（编号 `m1`…）和新对话，输出 `add / update / delete`；
   冲突的新说法改旧的那一条，记忆不会越积越乱。置顶的记忆自动整理永远不动。
4. **注入在 system prompt 末尾**：人格、日期等稳定前缀不变，上游前缀缓存仍然有效。说明文字要求自然运用、不复述、
   与最新说法冲突以最新为准、拿不准就确认——避免「念档案」和「硬说错」。
5. **只在私信里用**：评论是公开的，档案里的私事不能出现在公开回复里。第二期给记忆加敏感度后，公开场合只用标为公开的。
6. **只由管理员配置**（2026-10-25 决定）：用户端没有记忆面板、没有个人开关、没有无痕会话，只能在对话里让 AI 记住或忘掉。
   全站设置（开关、模型、提炼延迟、衔接时长、向量模型）在管理后台「AI 记忆」页，存在数据库里、随配置快照生效、改了记审计；
   用户要查看或删除自己的记忆时由管理员在同一页按用户处理。重置上下文只清当前会话，不清长期记忆。
7. **安全**：记忆当资料不当指令；提炼提示词明确不记敏感信息和「要求 AI 违反规则 / 改变设定」的内容；
   身份只来自可信的执行上下文（TOOL-004）；账号删除级联删除。
8. **计费**：摘要、提炼、整理、向量的调用不扣用户额度，也不计入全站每日额度（2026-10-25 决定），可以在后台选便宜的模型；
   记忆段让回复的 prompt 变长，这部分随回复按实际用量计费。

### 第二期的设计要点

1. **事件记忆按话题取回**：提炼时把具体的、有时间的事记成 `event`（带发生日期、重要度），每个角色单独记。
   回复前用最近两条用户消息检索，打分 = 相关度（关键词二元组重合 + 语义向量余弦）+ 时间 + 重要度，取前 6 条放进「相关往事」。
   近一周的大事（重要度 ≥4）无论话题都带上。
2. **不用 pgvector**：每个用户与每个角色的事件不超过 300 条，向量存在 `REAL[]` 列里，检索时在进程内算余弦——
   不需要数据库扩展和向量索引，开发、CI、生产的 PostgreSQL 都不用动。向量走 OpenAI 兼容的 `/embeddings`
   （后台指定提供方与模型，如 SiliconFlow 的 bge-m3）；没配就只按关键词检索，功能不缺。
   查询向量 4 秒超时，检索在准备事务之外，出错只是不带往事。
3. **待跟进让 AI 主动关心**：事件可以带「该问问结果的日子」。到期后，在会话开场或隔了 6 小时以上再聊时，
   让角色自然地问起最要紧的一件；问过就标记，不反复问；事情有了结果，提炼会更新那条事件。
4. **敏感度**：每条记忆 `private`（默认）或 `public`。评论区是公开的，只带 `public` 的档案与关系记忆，
   并明确要求不提私信里的事；事件、待跟进、摘要、衔接都不进评论区。

### 第三期的设计要点

1. **每晚整理**：像人睡觉时整理记忆一样，每天凌晨对旧事件多的（用户, 角色）做一次：零碎的同一件事合并成一条、
   从多条旧事里归纳出长期的认识（写成档案或关系记忆，如「对方常在深夜来聊天」）、丢掉以后不会再提的小事。
   只动一个多月以前的、后台提炼的、没置顶的事件；执行时来源在期间被改过就跳过。
2. **遗忘曲线**：不用模型，一条 SQL：低重要度、很久没更新、也很久没被想起的事件自动删除；被检索带进对话时记下「被想起」，
   常被想起的不忘；重要的、置顶的、让 AI 记下的永远不会被自动遗忘。
3. **翻聊天记录**：`recall_history` 工具在同一角色的全部会话原文里按关键词和日期找（「我们第一次聊的是什么」），
   直接用 PostgreSQL 的字符串匹配——每人每角色的聊天量不大，不需要全文索引或向量；重置过的会话只翻重置之后的。
4. **久别重逢**：隔了一周以上再来聊，角色会自然地说声好久不见。

### 分清人（2026-10-31 补充）

线上出现 AI 把对话里别人的名字当成用户马甲的情况。原因是转写只写「对方」「你」，提炼模型不知道「对方」是谁，
而档案的写法要求每条都以「对方……」开头，用户聊到的别人很容易被写成「对方叫 X」，再注入对话后与消息前的用户名对不上，
模型就把两者解释成同一个人的两个号。参考 mem0 图记忆（把「我」映射到用户 id）与 Graphiti（显式标出说话人、
只凭名字不能判定是同一实体）的做法，改为：输入开头写明「对方」是哪个账号；提示词要求关于别人的事写明是谁；
自动提炼与整理不记马甲、小号一类账号身份（代码兜底过滤）；记忆段说明记忆里的其他名字是别人。规则见 MEM-025。
没有给记忆加「主语」列：正文已经写明是谁，额外的结构收益不抵迁移成本，等需要按人检索时再评估。

### 数据模型

迁移 `20261113000001_ai_memory.sql`（第一期）与 `20261114000001_ai_memory_events.sql`（第二期），
说明见 `docs/schema.md`「AI 记忆」「AI 记忆第二期」：

- `ai_sessions` 加 `summary` / `summary_until` / `summary_epoch`（摘要随代际失效）与 `memory_until`（提炼进度）；
- `ai_memories`：`kind`（`profile` / `relation`）、`ai_user_id`（档案为空）、`content`（1–200 字）、`pinned`、
  `origin`（`extracted` / `told` / `manual`）、`source_conversation_id`；
- `ai_memory_settings`：全站设置，单行，管理后台维护，缺行按默认值；
- 第二期：`ai_memories` 加 `event` 种类、`sensitivity`、`importance`、`happened_on`、`follow_up_on`、`followed_up_at`、
  `embedding REAL[]`、`embedding_model`；
- 第三期：`ai_memories.recalled_at`、`ai_memory_pairs`（迁移 `20261115000001_ai_memory_consolidation.sql`）。

### 接口

全部在 `/v1/admin/ai/` 下，只给管理员，写操作记审计；用户端没有记忆相关的接口。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / PUT | `/v1/admin/ai/memory` | 全站设置（与统计） |
| GET | `/v1/admin/ai/memories?user=<id 或用户名>` | 某个用户的全部记忆 |
| DELETE | `/v1/admin/ai/memories/{id}` | 删一条 |
| POST | `/v1/admin/ai/memories/clear` | 清空某个用户的记忆（可按角色） |

不新增错误码。

## 考虑过的其他方案

| 方案 | 不选的原因 |
|---|---|
| 接站外记忆服务（mem0 云、Zep、Letta） | 私信原文要发给第三方；敏感度分级、待跟进、跨角色共享档案这些体验细节做不到 |
| 一开始就上向量库检索全部历史 | 档案与关系记忆量小，全部带上更准；事件记忆每人每角色几百条，进程内算余弦就够，不需要 pgvector |
| 事件检索用 pgvector + HNSW | 要给开发、CI、生产的数据库都装扩展；在这个规模下没有收益。将来单人聊天量大到字符串匹配变慢时再评估 |
| 只把历史窗口调大 | 成本线性增长，也解决不了换会话失忆 |
| 只靠模型在回复里调 `memorize` 写记忆 | 漏记多、误记多、拖慢回复；保留为用户明确要求时的入口 |

## 分期

| 期 | 内容 |
|---|---|
| 1（已实施） | 会话滚动摘要、跨会话衔接、档案与关系记忆、记住 / 忘掉工具 |
| 2（已实施） | 事件记忆与混合检索、待跟进事项与会话开场主动问起、记忆敏感度与评论区使用 |
| 3（已实施） | 每晚整理（合并、归纳、丢弃）与遗忘曲线、翻聊天记录的 `recall_history` 工具、久别重逢的问候 |
| 管理后台（已实施） | 「AI 记忆」页：全站设置与统计、按用户查看 / 删除 / 清空；去掉用户端的记忆面板、个人开关与无痕会话 |

## 测试

`crates/ai/tests/memory.rs`：长期记忆与衔接跟到新会话、另一个角色只共享档案、置顶的不被自动整理改动、冲突用 update；
窗口满了排摘要任务、摘要进 prompt、重置后作废；记住 / 忘掉当场生效且记在触发者名下、时间线事件；
管理后台：设置的默认值与校验、关掉后不读不写不提供工具、打开后恢复、按 id 或用户名查用户的记忆、删一条、按角色清与全部清、审计；
第二期：事件按话题取回（含假向量）、到期待跟进在新会话开场问起且只问一次、另一个角色看不到事件、remember 记事件；
第三期：翻聊天记录跨会话找到原文、重置之前的翻不到；隔 10 天再来是久别重逢且只提一次；每晚遗忘小事、排整理任务、
合并归纳丢弃与一周内不重复整理；`crates/ai/tests/comment.rs`：评论区只用公开记忆。
单元测试覆盖记忆段格式、摘要时机、开场判定、事件打分（关键词、向量、近期大事）、忘掉的匹配、提炼输出与整理方案的解析、关键词切分。
