# ADR 0003：旧数据导入（legacy schema + 单事务 INSERT … SELECT）

- 状态：已接受（2026-10-16）
- 背景：上线时一次性从旧 Strapi 5 库（PostgreSQL，约 25 MB）切换到新库（ADR 0001）。新旧表结构完全不同：
  Strapi 的关系存在 `*_lnk` 链接表里，媒体关联存在 `files_related_mph` 里，帖子有草稿行与发布行两份，
  时间列不带时区。

## 决策

1. **旧库整体恢复到新库的 `legacy` schema**（导出 → 临时库里把 `public` 改名为 `legacy` → 再导入新库），
   转换全部在库内用 `INSERT … SELECT` 完成，**一个事务**：要么全部导入，要么什么都不写。
   数据量很小，库内集合操作比逐行搬运快，也更容易审读。
2. **编译期检查覆盖旧库**：旧表结构由「在空库上启动旧后端、让它自己建表」得到，固定在
   `crates/legacy/sql/strapi-schema.sql`；映射规则写成 `legacy.ik_*` 视图（`sql/helpers.sql`）。
   开发库与 CI 加载这两个文件后，导入语句和其他代码一样用 `query!` 宏在编译期对照真实列检查。
3. **保留旧的整数 id**。新雪花 ID 远大于旧 id（见 `ik_kernel::id`），不需要映射表；
   帖子的草稿行与发布行按 `document_id` 合并，取最小的行 id。
4. **`ik-legacy` 是模块边界规则的明确例外**：它和 `migrations/` 一样直接写各域的表，
   只被 `ik-server legacy` 命令使用，任何业务域都不依赖它。
5. **时区必须显式给出**（`--legacy-timezone`，没有默认值）：Strapi 用 JS `Date` 写不带时区的列，
   存进去的是旧服务进程所在时区的墙上时间，只有运维知道那台机器的时区；预检会给出判断依据。
6. **先预检、后导入**：会让导入失败的数据（例如规范化后重复的邮箱）列为必须先处理；
   能按固定规则修正的（超长截断、非法用户名改名）自动修正并报告数量。
7. **媒体不搬家**：文件留在原来的对象存储里，`object_key` 从旧 URL 推出；真实哈希与尺寸在导入前
   由单独的、可续跑的步骤预先读取（读取对象存储是外部调用，不能放进导入事务）。

## 不迁移的数据

登录会话（令牌体系不同，所有人重新登录）、验证码、登录尝试、扫码状态、考试场次（通过状态已在账号上）、
旧的 AI 任务与配置（新系统的人格和模型通过 `ik-server ai import` 重新配置）、
热榜 UV 与阅读去重表（D-023）、Strapi 后台账号与权限表、操作队列（`report_actions`）、
通知桶（新系统读取时按 `bucket_key` 聚合）。

## 隐私

匿名评论引起的历史通知存着真实发送者，新表没有匿名分组（D-032 未建模），照搬会把匿名者的身份暴露在
「来自某人」的会话里。导入时把这类通知改为系统通知（去掉发送者，保留正文与链接），不丢数据也不越过
身份边界（AGENTS.md 规则 10、NOTIF-013）。

## 后果

- 加载顺序固定：`ik-server migrate` → 恢复 `legacy` schema → `legacy check` → `legacy import` →
  `search reindex` → 验收后 `DROP SCHEMA legacy CASCADE`。
- 旧后端的表结构如果在切换前还有变化，要重新生成 `strapi-schema.sql` 并重跑测试。
